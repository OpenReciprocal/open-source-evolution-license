# 核心创意

本页说明 OSEL 想成为的那种许可证。它不是许可证正文。

0.1 草案提出了这个方向，但没有把规则写到能够实行。
[`LICENSES/OSEL-0.2-draft.txt`](../../LICENSES/OSEL-0.2-draft.txt)
把同一创意写成一套可以闭合的机制。该文件是讨论稿，不修改 0.1。两份草案都不是 OSI 核准许可证。本页不是法律意见。

英文说明在 [evolution.md](../evolution.md)。两页不一致时以英文说明为准。说明与许可证正文不一致时，以正文为准。

## 一句话

任何接收方都可以把一个后代版本，置于一份更严格的、未经修改的 OSI 核准许可证之下，而这份许可证新增的义务必须落在一张固定菜单里。任何人不得把这个后代版本再放到更宽松的许可证下。任何人不得改写已经发布的祖先版本。

维护者不独占这条谱系的未来。未来也不能倒着走。

## 每一代都保留的东西

1. 收到软件的人可以使用、研究、修改并继续传递，包括收费，包括任何领域。
2. 贡献者已经作出的专利许诺继续有效，范围就是当时覆盖的权利要求。后来的演进不缩小它，也不把它扩大成贡献者没有作出的许诺。
3. 著作权声明，以及这条谱系曾经使用过的每份许可证文本，留在分发物里。过去读得到。
4. 祖先版本停留在它被发布时的条款上。演进只附着于记录里点名的那个后代。

## 可以改变的只有一件事

接收方分发一份仍处于 OSEL 之下的修改版本时，可以把该版本绑定到一份演进目标。

演进目标必须是未经修改的 OSI 核准许可证，并且同时满足：

- 保留声明义务；
- 至少增加菜单中的一项义务；
- 不增加菜单以外的义务；
- 不限制使用领域、个人、群体或商业模式。

收回“把后代再许可到更薄的许可证”的许可，是共享相似或源代码义务得以成立的方式。0.2 讨论稿写明了这一点。0.1 没有写明，它的再许可条款可以被读成绕过整个机制的旁路。

## 菜单

菜单是 OSEL 自己的清单，也是这个许可证真正的发明。点名若干份现成许可证，会做成另一种工具。菜单只接受这些新增义务：

| | 种类 | 内容 |
| --- | --- | --- |
| (i) | 署名 | 超出 OSEL 已有声明要求的署名与权利声明 |
| (ii) | 源代码 | 向谁、在何时、以何种形式提供源代码，包括共享相似 |
| (iii) | 专利 | 专利授予、专利报复性终止或专利抗辩 |
| (iv) | 名称 | 商标，或用名称来为修改版本背书 |
| (v) | 变更 | 标明修改版本，或说明改了什么 |

菜单之外的义务使演进不成立。常见的菜单之外：非商业限制、伦理使用禁令、国籍限制、为许可本身收费、源代码要等一段时间才变得自由、要求同一介质上的无关程序采用某种许可证。

准据法或法院条款不是菜单义务，也不能充当“至少新增的那一项”。0.2 讨论稿要求在菜单检验中忽略它们，避免一份许可证仅因法院选择就被放进或赶出菜单。

## 记录

只有在发出副本时附上演进记录，这一步才发生。博客、投票或提交说明不会让任何东西演进。

0.2 讨论稿里，源代码树的记录是根目录的 `EVOLUTION.md`。分发形式没有根目录时，用接收方通常会看到的同等显著声明。记录写明祖先许可证、正在演进的版本、目标、所依据的菜单项，以及迈出这一步的接收方。已有的段落保留。这个文件是日志，不是盖掉昨天的一张新贴纸。

0.1 要求的文件名是 `LICENSE-REPLACEMENT.md`，并且默认分发物有根目录。那个名字描述的是一次普通的再许可。0.2 的名字描述的是这个项目自己的行为。

## 三个场面

**Northwind 1.0。** 维护者在 OSEL 下发布一个库，不附加记录。每个接收方都可以在 OSEL 下发布自己的构建。演进是许可证交给他们的一项权力。许可证不强迫他们使用这项权力。

**Northwind 2.0，分叉。** 一名接收方加入了调度器，发布 2.0，并附上一份有效记录，指向一份 OSI 核准的共享相似许可证，其新增义务落在菜单内。已经拿到 1.0 的人，手里的 1.0 仍是 OSEL。这个分叉此后的 2.0 构建停留在目标许可证下。分叉不能再把 2.0 放到 MIT 下提供。贡献者在提交代码时已经允许这一步。他们不必为这一步再签一份授权。

**不会发生的那些步。** 有人宣布 Northwind 从此非商业。演进不发生：该限制在菜单之外。有人原样转发一份副本并称之为演进。演进不发生：0.2 只允许对修改版本迈出这一步，祖先和原样副本仍是 OSEL。有人填了一个目标，却指不出目标真正新增的菜单项。演进不发生。若该分发者只按这个失败的目标提供该版本，则该分发者违约。凡是在 OSEL 下收到软件的人，仍保留 OSEL 下的授权。

## 为什么用菜单，而不是一份名单

点名的许可证名单会过时，也会把政策藏进别人的文件。菜单用 OSEL 自己的话写出政策：新增义务可以关于署名、源代码、专利、名称和变更标记。其余是另一种许可证，即便某个登记处核准过它。

代价是：接收方在发布前必须自己把目标映射到菜单上。0.2 讨论稿不预先完成这张映射，也不宣布某一份具体许可证就是目标。一张自称完整的对照表，会把菜单冻成这份讨论稿拒绝成为的名单。0.1 的工作笔记仍在 [known-compatible-licenses.md](../compatibility/known-compatible-licenses.md)，它讨论的是 0.1 那套更严、也更无法适用的句子。

## 0.1 为什么还闭不上

0.1 把这一步叫做替换，然后要求目标的义务集合严格包含 OSEL 的义务集合。真实的许可证并不是这样一层层套进去的，于是这句活几乎放不进任何常见许可证，创意也无法被实行。0.1 同时给出一项再许可，它可以被读成允许退回 MIT。可以绕开的创意还不是机制。

0.2 讨论稿用菜单检验替换这一对句子，关上再许可旁路，并写上 0.1 起草说明里已经提出的专利规则：演进不扩大原贡献者的专利授予。迈出这一步的接收方只能传递自己持有的专利权利。

喂给讨论稿的逐条建议仍在 [proposed-0.2.md](../rationale/proposed-0.2.md)。讨论稿与那些建议不一致时，以讨论稿中组装好的文本为准。
